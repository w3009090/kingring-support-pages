# Правила работы с Codex Plugin

Этот документ является обязательным регламентом разработки, упаковки и
публикации плагина. Он нужен, чтобы GitHub, установочный ZIP и версия на сайте
всегда содержали один и тот же актуальный код.

## 1. Постоянные имена и идентификаторы

- Отображаемое название в WordPress: **Codex Plugin**.
- Репозиторий: `w3009090/kingring-support-pages`.
- Главная ветка: `main`.
- Техническая папка плагина: `kingring-support-pages`.
- Главный PHP-файл: `kingring-support-pages.php`.
- Slug и text domain: `kingring-support-pages`.
- Имя установочного и release-архива: **`CodexPlugin.zip`**.
- `Update URI`: `https://github.com/w3009090/kingring-support-pages`.

Техническую папку, главный PHP-файл и slug переименовывать нельзя. WordPress
использует путь `kingring-support-pages/kingring-support-pages.php` как
идентификатор. Его изменение создаст второй плагин вместо обновления
существующего.

## 2. Источник актуального кода

- Единственный источник для нового релиза — актуальный `main`.
- Перед началом работы нужно выполнить `git fetch` и сравнить локальный HEAD с
  `origin/main`.
- Нельзя собирать релиз из старого тега, старого ZIP или устаревшей локальной
  копии.
- Если версия на работающем сайте выше версии в GitHub, публикация запрещена,
  пока точные файлы установленной версии не перенесены в репозиторий и не
  проверены.
- Наличие более высокого номера версии само по себе не доказывает, что GitHub
  содержит актуальный дизайн и функциональность.
- Перед ручной заменой плагина нужно сохранить текущую папку плагина или иметь
  проверенный архив для восстановления.

## 3. Функции, которые необходимо сохранять

Если задача прямо не требует обратного, релиз должен сохранять:

- отдельные страницы `/support/` и `/contactus/`;
- редактирование содержимого через меню **King Ring Support** в WordPress;
- выбор темы обращения и необязательный номер заказа;
- загрузку вложений;
- согласие с политикой конфиденциальности;
- номера заявок;
- письма администратору и автоматические подтверждения пользователю;
- выбор логотипа и главного изображения;
- название **Codex Plugin**;
- автоматические обновления через GitHub Releases;
- год **2027** в футере, включая сохранённый маркер `{year}`;
- установленный формат архива `CodexPlugin.zip`.
- встроенное отключение блога и комментариев с переключателями в настройках
  Codex Plugin.
- при включённом отключении блога главная с режимом «последние записи» должна
  перенаправляться на `/support/`, без требования назначить статическую страницу;
- Codex Plugin не должен показывать предупреждение о необходимости статической
  главной страницы.

FAQ удалён и не должен возвращаться без отдельного запроса.

## 4. Версионирование

Для каждого релиза одновременно обновляются:

1. `Version` в заголовке `kingring-support-pages.php`.
2. `KINGRING_SUPPORT_PAGES_VERSION` в том же файле.
3. `Current version` в `README.md`.
4. Git-тег в формате `vX.Y.Z`.

Тег должен точно соответствовать версии плагина: версия `2.4.8` публикуется
тегом `v2.4.8`. Новая версия всегда должна быть выше установленной версии и
последнего публичного релиза. Уже опубликованный тег не перемещается и не
используется повторно; исправление выпускается новой patch-версией.

## 5. Содержимое ZIP

Release asset должен называться точно **`CodexPlugin.zip`**. В корне ZIP должна
находиться папка `kingring-support-pages`, а внутри неё:

- `kingring-support-pages.php`;
- `README.md`;
- `assets/`;
- `templates/`.

В архив нельзя помещать `.git`, рабочие файлы, временные файлы, секреты,
локальные конфигурации или каталог `downloads/`.

## 6. Обязательные проверки до публикации

Перед коммитом и тегом необходимо:

1. Запустить PHP lint для всех PHP-файлов.
2. Проверить YAML workflow `.github/workflows/release.yml`.
3. Выполнить `git diff --check`.
4. Собрать ZIP и выполнить `unzip -t`.
5. Сравнить файлы внутри ZIP с файлами коммита, из которого создаётся тег.
6. Проверить в упакованном PHP-файле название, версию, год 2027 и фильтр
   `auto_update_plugin`.
7. Проверить `/support/` и `/contactus/` функциональным тестом или в WordPress.
8. Для изменений формы проверить отправку, валидацию, вложения, номер заявки и
   автоответ.
9. Убедиться, что рабочее дерево не содержит случайных изменений.
10. Для встроенного отключения блога и комментариев проверить меню администратора,
    публичные URL, главную в режиме «последние записи», поиск, REST API и отсутствие
    комментариев.

Нельзя публиковать релиз только на основании успешной сборки ZIP.

## 7. Порядок публикации

1. Закоммитить проверенные изменения в `main`.
2. Отправить `main` в GitHub.
3. Создать аннотированный тег `vX.Y.Z` на том же коммите.
4. Отправить тег в GitHub.
5. Workflow `Publish plugin release` должен собрать `CodexPlugin.zip` и создать
   GitHub Release.
6. Скачать asset именно из GitHub Release.
7. Проверить имя файла, целостность ZIP и совпадение содержимого с тегом.
8. Убедиться, что страница релиза и ссылка загрузки доступны публично.

Коммит `main`, тег и содержимое release asset должны представлять одну и ту же
версию.

## 8. Автоматические обновления WordPress

- Плагин получает последний публичный GitHub Release через GitHub API.
- WordPress устанавливает обновление только если версия релиза выше
  установленной.
- Установочный asset выбирается в первую очередь по имени `CodexPlugin.zip`.
- Автоматические обновления принудительно разрешены только для этого плагина.
- Свежий успешный ответ GitHub кэшируется на один час.
- Устаревший кэш с версией ниже установленной удаляется немедленно.
- При обновлении плагина очищаются собственный release-кэш и WordPress-кэш
  обновлений.
- Ссылка **Check Updates** рядом с **View details** очищает оба кэша и немедленно
  запускает стандартную проверку обновлений WordPress.
- Ручная проверка доступна только пользователю с правом `update_plugins` и
  защищена WordPress nonce.
- Фоновая проверка WordPress обычно выполняется примерно каждые 12 часов и
  зависит от WP-Cron и посещаемости сайта.

При необходимости немедленной установки используется **Plugins → Add Plugin →
Upload Plugin**, затем загружается `CodexPlugin.zip` и подтверждается замена
текущего плагина.

## 9. Окно View details

Окно **View details** должно показывать название **Codex Plugin** и актуальную
версию последнего GitHub Release. Нельзя возвращать закэшированную версию ниже
установленной. После изменения механизма обновлений нужно отдельно проверить
вкладки Description и Changelog.

## 10. Восстановление и откат

- Предыдущие GitHub Releases и теги не удаляются.
- Перед откатом проверяется содержимое старого asset, а не только номер тега.
- Если опубликован неправильный пакет, создаётся новая patch-версия с актуальным
  кодом; существующий тег не переписывается.
- Нельзя устанавливать старый ZIP поверх более новой рабочей версии без
  подтверждённой резервной копии.
- После восстановления актуальный код обязательно сохраняется в `main`, чтобы
  следующий релиз снова не заменил сайт устаревшей версией.

## 11. Безопасность

- Секреты, пароли, SMTP-данные и WordPress application passwords не хранятся в
  GitHub и не включаются в ZIP.
- Все входные данные формы проходят WordPress-санитизацию и проверку nonce.
- Тип и размер вложений должны проверяться до отправки.
- Обновления загружаются только по HTTPS из публичного GitHub Release.
- Нельзя отключать TLS-проверку или обходить проверку целостности ради успешной
  публикации.

## 12. Краткий release checklist

- [ ] `main` содержит актуальный сайт и все последние функции.
- [ ] Версия повышена во всех трёх местах.
- [ ] Название плагина — `Codex Plugin`.
- [ ] Год в футере — 2027.
- [ ] ZIP называется `CodexPlugin.zip`.
- [ ] Внутренняя папка — `kingring-support-pages`.
- [ ] PHP, YAML, ZIP и функциональные проверки прошли.
- [ ] Встроенные Disable Blog и Disable Comments работают без отдельных плагинов.
- [ ] Коммит отправлен в `main`.
- [ ] Тег указывает на тот же коммит.
- [ ] GitHub Release создан и доступен публично.
- [ ] Скачанный release asset совпадает с исходниками тега.
